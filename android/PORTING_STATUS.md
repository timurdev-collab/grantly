# EduT Android port status

Updated: 2026-10-30. Source branch: `feature/android-compose-foundation`.
Design and behavior reference (read-only): `design/home-concept-02`.

## Implemented in Android source
- Approved advisors now have a separate **Advisor Portal** screen reachable from their Profile. The portal shows identity-scoped counts for active students, registration requests and open consultations, with dedicated Students and Consultations sections and Back navigation. Counts are read-only, fail closed when the advisor role cannot be verified, and exclude unknown statuses. This is a partial Android navigation improvement, **not** iOS role-specific launch/navigation parity; Messages remains a separate bottom tab and video calls are not implemented. Authenticated-account and physical-device verification are pending.
- The Android Advisor Portal now includes a **read-only Professional profile** section. It reloads the current user's advisor profile through the existing authenticated row-scoped API and checks both advisor role and approved status before displaying professional details. No editing or photo replacement is implied, and authenticated-account/device verification remains outstanding.
- Advisor-role profile includes an incoming consultation queue backed by the existing identity-scoped `advisor_consultation_requests_for_me` RPC. It displays service, student name, topic, status, price, preferred timestamp, focused status filters, 20-at-a-time paging and manual refresh. Advisors can now confirm a **paid** consultation and complete a **confirmed** consultation through the existing `advisor_update_consultation_request` RPC after a confirmation dialog and a fresh advisor-scoped status check. Android does not permit advisor payment verification, arbitrary status changes or cancellation. The existing RPC does not atomically enforce the expected previous status, so concurrent status changes remain possible between the client preflight and server mutation. Contact email, WhatsApp and private notes are deliberately discarded from the response; no contact links or calls are offered. These actions are **source-only, partial iOS parity** and still require authenticated live-account and physical-device testing.
- Advisor-role profile now has a **My advisor students** overview using the existing identity-scoped `advisor_my_students` RPC, with requested/active counts, status filters, and 20-at-a-time display. Android also offers confirmed accept/decline/end-advising actions through the existing `advisor_manage_student` RPC, checking the advisor role and refreshing the assignment before sending each decision. The RPC itself does not enforce expected old status, so a concurrent change between preflight and mutation is still possible; authenticated test accounts and device verification are required before relying on these actions. Verified-payment contact links, calls and full iOS Advisor Portal parity remain outstanding.
- Compose home layout and bottom navigation.
- Home 'Closing soon' now reads the first 100 published scholarship results sorted by the existing Deadline RPC, filters invalid/missing/past ISO dates locally, and displays up to three clickable upcoming scholarships with official-source caution. This is a read-only catalog preview, not an exhaustive deadline index or a reminder service; it needs live API/device verification.
- Read-only scholarship discovery through the existing public Supabase RPC.
- Server-side search, degree/country/field/funding filters, sorting and pagination.
- Scholarship detail tabs for overview, eligibility, benefits and application information.
- Profile-tab email/password sign-in, signup and sign-out through the existing Supabase Auth API.
- Signup now uses a complete authenticated session returned by Supabase when email confirmation is disabled; when the signup response contains no tokens, Android shows email-confirmation instructions instead. Partial or mismatched sessions are rejected. This requires live-account/device verification.
- Authenticated Applications list showing saved scholarships, status and notes (20 records per page with explicit Load more).
- Authenticated application status and notes editing through existing user-scoped APIs.
- Application task checklist: read, complete/reopen, add custom tasks, confirm before deleting custom tasks, and set/change/clear task due dates using existing `application_tasks` RLS table (not yet device-tested; first 100 tasks per scholarship). Due dates use the existing `due_at` timestamptz column, store the selected day at local noon and display in the device time zone; travel/time-zone changes may alter the displayed calendar day. No reminder notifications are scheduled.
- Personal application target dates can now be viewed, selected using the native Android date picker, changed or cleared from saved scholarship cards. Writes are scoped to the signed-in user's `saved_scholarships` row and use the existing `personal_deadline` date column under RLS. This does not change official provider deadlines, does not send Android reminders and remains unverified with a live account/device.
- Private application document metadata, single-file uploads and confirmed deletion via the existing user-scoped RLS table and private Storage bucket (PDF/JPEG/PNG/HEIC/HEIF, up to 6 MiB). Upload failure attempts storage rollback; all mutations remain unverified on a live account/device.
- Save/remove scholarship controls on detail screens using existing user-scoped Supabase RLS policies (not yet device-tested).
- Automatic access-token refresh and Android Keystore AES-GCM encrypted session persistence, including restoration at launch and local token removal on sign-out (not yet device-tested).
- Password recovery email requests, verified recovery deep links and password update through the existing Supabase Auth API (not yet device-tested).
- Private academic profile summary and validated editing through the existing `student_profiles` RLS table; degree, GPA, IELTS, graduation, residence, nationality, major and study preferences. Role is read-only and never included in update payloads (not yet account/device-tested).
- Signed-in account deletion is now wired for all roles through the existing iOS `delete-account` Edge Function. Android requires a destructive confirmation, waits for `{deleted:true}` before clearing local session credentials, and does not modify server code. This flow is **source-only**, not yet tested with a disposable real account or physical device; do not rely on it as verified until that test is completed.
- Read-only approved advisor directory, reachable from the Home guidance card after sign-in. Uses existing authenticated `available_advisors` RPC, with local search and advisor detail summaries (not yet live-account/device-tested).
- Read-only advisor consultation service options (duration, live price and discount) and authenticated consultation-request history (status, advisor, topic and quoted price), using existing `available_advisor_services` and `my_advisor_consultation_requests` RPCs (not yet live-account/device-tested).
- Personalized scholarship recommendations through the existing `get_my_scholarship_matches` RPC, including ranking, explanations and eligibility warnings (not yet live-account/device-tested).
- Advisor consultation booking requests using the existing policy-acceptance and booking RPCs. Displays three policies, records versioned consent, allows service and local preferred date/time selection, and sends the chosen instant in UTC with the device time zone. No in-app payment or guaranteed booking; requires live-account/device testing.
- Read-only authenticated Community feed reachable from Home, loading visible non-story posts in 30-post pages through existing social_posts RLS with manual refresh, explicit Load more, caption and media-presence indicators. Pagination preserves already loaded posts and deduplicates by post ID. Community post comments now support viewing the first 100 visible comments, writing a 1–1,000 character comment, and deleting your own comments with confirmation through existing RLS policies. Community now includes like/unlike controls using existing social_post_likes RLS, with batched lookup of the signed-in user's likes, per-post busy states and error recovery. Text-only post creation (1–2,000 characters) now uses the existing social_posts insert policy; publishing is denied by the server unless the author has a visible Community profile. Own text-only Community posts can now be edited (caption only, 1–2,000 characters) and deleted after confirmation using user-ID-scoped, kind-scoped and media-null-scoped PATCH/DELETE under existing RLS. The feed also checks legacy media_url when identifying media, so media posts cannot accidentally be edited or deleted without Storage cleanup. Private Community photo preview is now wired to the feed for posts with an image media_path: Android requests a one-hour signed URL from the existing private social-media Storage bucket, checks the Supabase host, rejects redirects and oversized images, and downsamples decoded bitmaps. This read-only photo flow is not yet live-account/device-tested and does not handle legacy media_url. A read-only private Community video preview now downloads supported MP4/MOV/M4V media_path clips to app-private temporary cache with a 200 MiB limit, signed Storage URLs, strict same-host checks and no redirect following; Android VideoView plays the local file and cleanup runs on exit. The video flow is not yet live-account/device-tested, may reject large videos and does not support legacy media_url, uploads, stories or community profile editing; no author cards; hidden community profiles may yield an empty feed. Community post reporting is now available for other authors' visible posts, using the existing RLS-protected `social_post_reports` insert policy and iOS-equivalent reason choices (one report per reporter/post). Feed actions are horizontally scrollable on narrow screens. Community, comment, like, text-post creation, editing, deletion and post-report mutations have not been account/device-tested.
- Resumable MP4 video-upload implementation: Android now stages a content-provider video in app-private cache with a 200 MiB cap, verifies its MP4 container signature, creates a TUS upload at a validated Supabase Storage origin, uploads 6 MiB chunks and reconciles server offsets with HEAD before retrying interrupted PATCH requests. Community posts, stories and Shorts now use this path for MP4. The staging file is deleted on completion/failure. This is **source implementation only**: no authenticated upload, resume/retry or physical-device test has been completed; upload progress is shown during chunk transfer, and the composer now offers cancellation with best-effort private-media cleanup while upload is in progress. A process restart still cannot resume an unfinished session; cancellation and rollback are not yet device-verified. Community profile checks and text-post publishing now reject HTTP redirects instead of following them with authenticated requests. These safety changes need CI and emulator/account verification.
- Bounded Community media publishing now supports JPEG/PNG photos (up to 6 MiB) and MP4 videos (up to 200 MiB through TUS) for regular posts and 24-hour stories, using the existing private social-media Storage bucket and social_posts insert RLS. Android verifies media signatures rather than trusting provider MIME types, checks Community profile visibility before uploading, and attempts Storage rollback when the database insert fails. This is **partial** iOS parity: Android now has an in-session resumable MP4 path up to 200 MiB, but does not compress or transcode videos, cannot recover a session after process death, and has not been verified with live Storage or a device. HEIC, long videos and media-post deletion are not implemented. MP4 Shorts publishing is now supported in source (up to 200 MiB, video-only), with format restrictions covered by unit tests; it is not device/account-verified. Uploads and story playback remain unverified with an authenticated account or device.

- Community posting access now performs a read-only authenticated lookup of the signed-in account's existing community_profiles.is_visible flag. The Create post button is disabled when the profile is hidden, absent, or the lookup fails; transient lookup errors offer a retry. This does not unhide profiles, change the iOS 1.0 release policy, or bypass server RLS. The eligibility check and posting flows still require real-account/device verification.
- Community stories rail queries up to 24 active, unexpired story posts using existing authenticated social_posts RLS, checks expiry again locally, and opens supported private photo/video previews or text-only stories. Single-photo story publishing (JPEG/PNG, up to 6 MiB) now reuses the existing private social-media Storage uploader, existing visible-profile preflight and RLS, with a 24-hour UTC expires_at matching iOS; failed inserts attempt Storage rollback. Story publishing requires an image, as on iOS. MP4 video story uploads (up to 200 MiB through TUS) are implemented in source, but no video transcoding, author cards, story progress/timing UI, or legacy media playback; requires authenticated live-account/emulator/device testing.
- Advisor directory and message inbox now intercept Android system Back within nested advisor profile, booking, consultation-history and message-thread screens; the inbox refreshes after returning from a conversation. This aligns the back-navigation expectation with iOS NavigationLink but has not yet been device-tested. The directory root still delegates Back to Home.
- Home notification bell now displays a bounded unread-count badge (1–9, then 9+) using a user-scoped read of up to ten existing unread notification IDs. It refreshes when Home is shown and after returning from the inbox; it does not poll in the background or register push devices. Live-account/device verification is pending.
- Home notification bell now opens an authenticated in-app inbox backed by the existing `app_notifications` RLS table. Android supports paginated reading (30 per page), refresh, individual mark-read and mark-all-read using user-ID-scoped PATCH requests. This does not register Android push devices, schedule new reminders, or change server notification preferences; it requires live-account/device testing.
- The in-app notification inbox now opens a preferences screen for deadline reminders, task reminders, advisor messages and scholarship matches. Settings are loaded from and upserted to the existing user-scoped `notification_preferences` table; absent rows display the schema's default enabled values until the first save. Switches commit only after a successful server response. No Android push registration or backend schema change; authenticated account/device verification remains outstanding.
- Advisor-only Messages tab with authenticated conversation summaries, unread counts, paginated messages, manual refresh, read receipts and explicit message sending. Approved advisor profiles can open or create advisor-direct conversations through the existing role-restricted RPC. Foreground-only inbox polling (30 seconds) and thread polling (20 seconds) now refresh content while visible; thread updates preserve older paginated messages. Android includes user/message safety reports and block/unblock controls through existing RLS-protected tables, including a block confirmation and disabled composer for locally blocked users. Polling is not a realtime subscription or push notification; messaging and safety actions are not live-account/device-tested.

The Android Professional profile section is therefore read-only; do not bypass this with direct PATCH or mutate the production backend without separate authorization.

## Preview safety
Authentication tokens are stored as AES-GCM ciphertext using a non-exportable Android
Keystore key; app backup is disabled. On restart, the app attempts to restore and refresh
the encrypted session. Sign-out clears local credentials before contacting the server.
If Keystore storage is unavailable, the app keeps an in-memory session only. The
persistence flow has not yet been verified on a physical Android device.

The iOS `design/home-concept-02` HomeView currently emphasizes scholarship matches, deadlines and advisors; Android's Community shortcut is an additional preview entry point, not verified iOS Home visual parity.

A successful `Android Debug APK` GitHub Actions build proves compilation only, not
feature parity, server availability, account behavior or device compatibility.
Do not distribute the debug APK as a production release.
